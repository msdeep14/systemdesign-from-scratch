# Chapter 04: Caching

## Why Caching - The Two Read Replica Bottlenecks

Read replicas distribute read traffic across multiple database instances. But two fundamental limits remain that replicas cannot solve:
1. Repeated disk reads. With replicas, you split the disk reads across machines. But the total number of disk reads stays the same. Use `benchmark_repeated_reads.py` script to demonstrate this.
2. WAL sender overhead. PostgreSQL streaming replication works by the primary streaming WAL (Write-Ahead Log) records to every connected replica. Each replica gets its own walsender process on the primary. Use `benchmark_wal_sender_overhead.py` with different number of replicas script to demonstrate this.

> [!WARNING]
> **App Server Rolling Restart Delay**
> When you change the replica count, the replica IPs change. Terraform automatically updates the App Server's Launch Template and triggers an **Instance Refresh** on the Auto Scaling Group. This does a rolling replacement of the App EC2 instances so they get the new `.env` with the updated `REPLICA_DB_HOSTS`. 
> 
> This rolling replacement takes 3-5 minutes. During this window, old app servers might still try to connect to the old replicas that were just destroyed, resulting in `OperationalError: connection timed out` in the logs.
> **Fix:** Simply wait ~5 minutes for the ASG to finish replacing the instances before running the benchmark.
> or terminate the EC2 instances, the ASG will bring back new instances with updated configuration.

> [!IMPORTANT]
> **Production Infrastructure Flaw: Hardcoded Replica IPs**
> The current architecture hardcodes replica IPs into the App Servers' environment variables. In a real production environment, this is an anti-pattern. If we scale down from 3 replicas to 1, Terraform destroys the extra replicas immediately, but the old App Servers continue to route traffic to dead IPs until the 5-minute ASG roll completes, causing significant downtime.
> 
> **Future Fix:** To decouple the App Server lifecycle from the Database lifecycle, we will later explore using the deployed **Consul** architecture for Service Discovery, alongside NGINX or an AWS NLB. This will allow the App Servers to point to a single static endpoint, while replicas dynamically register/deregister themselves without requiring App Server restarts.

### Benchmark 3: Thundering Herd (Concurrent Cache Misses)

A "Thundering Herd" (or Cache Stampede) occurs when a popular cache key expires or is empty, and hundreds of concurrent requests all miss the cache simultaneously. Without protection, all hundreds of requests will hit the database at the exact same millisecond to generate the same feed, instantly overwhelming the database CPU.

**The Fix: Cache Promises (Mutex Locks) & Device Caching**
To solve this, we implemented a **Cache Promise** pattern in `newsfeed/views.py` using a short-lived Redis lock (`SETNX`). 
1. Only the *first* request to miss the cache acquires the lock and queries the database.
2. The remaining concurrent requests ("the herd") fail to get the lock and enter a short polling loop waiting for the cache to be populated. *(Note: In Chapter 6, we will upgrade this polling loop to use Redis Pub/Sub for zero-latency wake-ups as recommended by [Redis best practices](https://redis.io/blog/caches-promises-locks/)).*
3. **Device Caching Fallback**: If the polling times out (e.g. the heavy query takes too long), returning an empty feed (HTTP 200) would wipe the user's screen. Instead, we return an **HTTP 503 Service Unavailable**. Combined with the `@cache_control(stale_if_error=86400)` headers we added, this ensures compatible browsers and CDNs seamlessly serve the user's previously cached device feed rather than breaking the UI.

**Replication Steps:**

You can run this benchmark locally to see the Cache Promise in action. The script fires 50 concurrent requests immediately after clearing the cache.

```bash
# 1. Ensure your local DB has the pg_stat_statements extension enabled
docker exec photoz-db-1 psql -U postgres -d bses -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"

# 2. Run the benchmark script
python chapter04/caching/benchmark_thundering_herd.py
```

**What to look for in the output:**
The script checks `pg_stat_statements` on the primary DB. Even though 50 concurrent requests missed the cache simultaneously, you should see exactly **1 Heavy Feed Query Executed**. The Cache Promise successfully held back the other 49 requests and protected the database! 

#### Testing the 503 Device Caching Fallback & RYW Edge Case

To see the device caching fallback and the Read-Your-Writes edge case in action, you can artificially delay the cache promise:

1. Open `photoz/newsfeed/views.py` and add a temporary `time.sleep(15)` inside the lock acquisition block:
   ```python
           if acquired:
               import time
               time.sleep(15) # <--- ADD TEMPORARY DELAY
               try:
   ```
2. Restart the web container so the changes take effect: `docker compose restart web`
3. Clear the Redis cache manually: `docker exec photoz-redis-1 redis-cli FLUSHALL`
4. Run the benchmark script again: `python chapter04/caching/benchmark_thundering_herd.py`

**What to look for:**
- You will see exactly **2 successful requests** (HTTP 200). The first request grabs the lock, and the 50th request grabs the lock 5 seconds later after it expires.
- The other **48 requests** will instantly timeout from the polling loop and return our `503 Service Unavailable` fallback (which Nginx intercepts and masks, returning 404/503). This proves the device caching fallback works and prevents the server from overwhelming the DB or wiping the user's screen.
- **RYW Edge Case:** The script will report **0 Heavy Feed Queries Executed**. Why? Because the login script sets a 5-second `force_primary` Read-Your-Writes cookie. By sleeping for 15 seconds, the RYW TTL expires *before* the heavy query executes. Django's router sends the delayed heavy query to the **Replica DB**, completely bypassing the Primary DB's `pg_stat_statements` check!

### Summary of Benchmark Results

Based on our benchmark data:

1. **Repeated Disk Reads:** 
    - **Before Caching:** Out of 30 sequential HTTP requests to the Newsfeed, the `pg_stat_statements` recorded 12-15 executions on the primary (due to the replica router routing the others to replicas). For those requests, the exact same heavy DB query ran repeatedly, consuming disk and DB CPU each time. Without caching, $N$ requests = $N$ DB queries.
    - **After Redis Caching:** Out of 30 sequential HTTP requests, the heavy feed calculation query executed exactly **1 time** (the initial cache miss). Redis successfully served the feed structure for the remaining 29 requests. The fast pagination queries (`WHERE id IN (...)`) executed ~15 times on the primary, proving two things:
        1. **Write-Around Pattern:** The heavy photo objects bypass Redis and are read directly from PostgreSQL via the highly optimized `IN` query.
        2. **Read-Your-Writes Middleware:** The primary DB only saw 15 reads because the login (`POST`) locked reads to the primary for 5 seconds. The remaining 15 reads were cleanly offloaded to the read replicas once the lock expired.

2. **WAL Sender Overhead (Replica Ceiling):**
    - **1 Replica:** 50,000 writes generated **8.14 MB** of WAL. Peak write lag was **14.75 ms**. Primary ran 1 `walsender`.
    - **2 Replicas:** 50,000 writes generated 19.39 MB of WAL (higher due to background processes/autovacuum). Primary streamed a total of **~38.79 MB** outbound WAL. Peak write lag doubled to **30.33 ms**. Primary ran 2 `walsender`s.

## Note on pg_stat_statements

`benchmark_repeated_reads.py` connects directly to the primary on port 5432 to read `pg_stat_statements`. This view requires:

1. `shared_preload_libraries = 'pg_stat_statements'` in `postgresql.conf` (set in `postgres-init/02-setup-replication.sh`)
2. `CREATE EXTENSION pg_stat_statements;` run once (in `postgres-init/01-pgbouncer-auth.sql`)

For an existing deployment where the DB was not initialized with these scripts, enable it manually:

```bash
# SSH into the DB EC2 instance
docker exec -it photoz-db-1 psql -U postgres -d bses -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"

# Then add to postgresql.conf and restart the container
docker exec -it photoz-db-1 bash -c "echo \"shared_preload_libraries = 'pg_stat_statements'\" >> \$PGDATA/postgresql.conf"
docker exec -it photoz-db-1 bash -c "echo \"pg_stat_statements.track = all\" >> \$PGDATA/postgresql.conf"
docker compose -f docker-compose-db.yml restart db
```

## Verifying Redis Cache Manually

To manually inspect the data inside Redis (to prove the caching architecture is working), you can use the Django shell from inside one of your App Node containers:

```bash
# 1. SSH into one of your App Nodes
ssh -i ~/.ssh/id_rsa ubuntu@<app-node-public-ip>

# 2. Enter the running Django container
docker exec -it photoz-web-1 bash

# 3. Open the Django python shell
python manage.py shell
```

Inside the python shell:
```python
from django.core.cache import cache
client = cache.client.get_client()

# 1. See all keys matching "feed"
keys = client.keys('*feed*')
print(keys) 
# Example output: [b':1:feed:1']  
# (The 'b' means byte-string, ':1:' is django's cache prefix, and 'feed:1' is the timeline for user ID 1)

# 2. Check the Redis data type (should be a List for Fan-out on write compatibility)
if keys:
    print(client.type(keys[0])) 
    # Output: b'list'

# 3. View the actual cached photo IDs in the timeline
if keys:
    print(client.lrange(keys[0], 0, -1))
    # Output: [b'45', b'44', b'42', ...]
```
